# 架构设计详解

## 数据流

```
Agent A 关闭
    ↓
Watcher 轮询 tasklist（15s，进程名比较不区分大小写）
    ↓
检测到 A 从有到无 → 等 3s（释放文件句柄）
    ↓
sync.py --apply
    ↓
┌────────────────────────────────────────────────────────┐
│ 1. 适配器读取三端会话，归一为 canonical 格式          │
│ 2. 过滤自动化会话（标题匹配）                         │
│ 3. ID 归一：bare_id + 映射表折回                      │
│ 4. 取并集，逐端分类：                                 │
│      import = 该端没有这条会话                        │
│      tail   = 该端有，但缺尾部消息                    │
│ 5. tail 过滤：时间戳 > 该端已有最大值 且 指纹不在该端  │
│              再剔除该端物理装不下的角色               │
│ 6. 门禁：目标 agent 进程存活 → 该端本轮整体跳过       │
│ 7. 备份目标存储                                       │
│ 8. 写入（整条新建 / 尾部追加）                        │
│ 9. 读回验证，重算差异                                 │
└────────────────────────────────────────────────────────┘
    ↓
Agent B 打开 → 看到 A 的对话，且 A 后来新增的那些句子也在
```

## 为什么不用服务端

agentctxsync 的完整方案是 FastAPI + PostgreSQL + TLS 反代，为跨设备设计。
单机场景下：
- 多一个进程 = 多一个挂的环节
- 多一个数据库 = 多一个备份/迁移负担
- 网络依赖 = 断网不可用
- 认证/密钥 = 不必要的复杂度

本方案：一个 Python 脚本 + 文件系统，零依赖外部服务。

## 为什么事件驱动 + 心跳兜底

纯定时同步的问题：agent 运行中的写入会被它的内存态覆盖；没有新对话时也在空跑。
纯事件驱动的问题：退出事件可能漏——进程崩溃、watcher 自己没起来、或那次同步失败了。

所以两级都要：退出事件负责低延迟（关掉 A 打开 B 时 B 已经齐），每 900s 一轮全量心跳负责收敛。心跳的代价是一次读取 + 一次比较，没有差异时不写任何东西。

## tail 算法

目标端已有同一会话时，只补尾部，判定条件是两条的与：

1. `ts(msg) > tmax(target)` —— 目标端最大时间戳之后的消息才算候选（该端已经说完的部分不再看）。
2. `ckey(msg) not in have(target)` —— 内容指纹 `(role, sha1(text.strip().lower())[:16])`，**不含时间戳**。

第 2 条是幂等的关键。同一句话被写入不同端时时间戳可能差几毫秒甚至被改写，只用时间戳判重，重跑一次就把同一条消息又写一遍。指纹兜住了这点：实测三条通道重放写入都是 0。

写入前对目标会话取一次快照，写后读回再算一次 tail——剩余应为空。

## 角色可承载性

三端消息角色的实测分布（本机，仅作格式判定依据）：

| 端 | 出现过的角色 |
|---|---|
| Qoder | assistant / user / system |
| DSH | assistant / user（v4 事件流没有 system 的位置）|
| WB | assistant / tool / user |

因此 `ROLES_LOST = {"DSH": {"system"}, ...}`：DSH 物理存不下 system 消息。这类消息若不剔除，每轮都会重新进入计划，差异永远降不到 0；若剔除后不报告，就是在藏丢失。现在的处理是剔除 + 单独统计上报（`Physically unwritable: N msg(s) (role: system)`），面板里用灰色标注、不计入差异。消息本身保留在能承载它的端。

## 进程门禁：失败方向决定安全性

写入门禁查询目标 agent 是否在运行。这里唯一的危险方向是**把「开着」看成「关着」**——那样会直接往活动存储里写，app 下一次提交覆盖掉写入结果，甚至写坏。

两个细节：
- `tasklist` 回报的镜像名带它自己的大小写（过滤 `notepad.exe` 会返回 `Notepad.exe`），所以比对必须转小写；否则一次匹配不上就等于"没在跑"。
- 三端各自独立门禁：WB 关闭即可写 WB，不影响 DSH/Qoder 的判断。

## Qoder 写入的三层保护

Qoder 的会话行在 sqlite 里，运行中确实可写（WAL），但**会话被 app 打开时不可写**：app 把那条评论加载在内存里，下一次回合提交会用自己的版本覆盖外部写入。所以：

1. 进程存活 → 本轮 Qoder **整体**不写（比"只跳过打开的那条会话"更保守：app 同时可能持有多个标签页，判定到具体哪条在内存里不可靠）。判定在 sync.py 内部完成，不依赖调用方传参，所以 watcher 和面板都只跑 `--apply`；另有 `--defer-qoder` 手工开关，用于进程明明关着但仍想强制不动 Qoder 的场合（做实验、临时避险）。推迟的尾部只报不写，等 Qoder 退出那一次事件再落。
2. `--live-guard N` → 即使进程已判定关闭，仍跳过 `chat_sessions.updated_at` 在 N 分钟内被改动过的会话（防止刚关完还没落盘、或多实例）。
3. 写前整库备份 + `BEGIN IMMEDIATE` 事务；插入消息时写 `payload_json{parts}` / `payload_hash` / `payload_schema_version=2` / `source='cli-import'`，序列号接续。

会话 ID 还要过一层映射：原生导入器给同一对话分配了新 ID，所以 tail 命中的 canonical id 必须先在 `qoder_id_map.json` 里折回真实 `session_id`，映射不到就报 `session-missing` 而不是瞎猜。

## 去重策略

三层：
1. **ID 归一化**：去掉 `session-` 前缀，统一为 bare UUID
2. **映射表**：Qoder 原生导入器会分配新 ID，用 migration_ledger 的 source_ref → target_session_id 映射回原始 ID
3. **权威源优先**：同一 ID 在多端都有时，取权威源（WB）的版本

## 控制台与弹窗

watcher / 面板从 `pythonw.exe`（隐藏的启动 `.vbs`）启动，父进程没有控制台。这种父进程再启动子进程时，Windows 会**分配一个新控制台**；如果系统默认终端是 Windows Terminal，实际表现是 `svchost.exe` 拉起 `WindowsTerminal.exe` + `OpenConsole.exe`，屏幕上闪一个窗口然后关闭——同步每触发一次就闪一次。

修复是所有 subprocess 调用统一带 `creationflags=CREATE_NO_WINDOW`（改为分配一个隐藏控制台）。

取证时注意两点：那两个窗口宿主进程**不是**请求方的子进程，靠父子链归因抓不到，只能按时间窗对齐 spawn 事件；对照实验要把 worker 和采样器放在同一个时钟、同一台机器的 ASCII 路径下跑，否则 `.vbs` 的本地编码会把非 ASCII 路径读坏。A/B 结果：不加 flags 的一次同步批次里出现 4 次窗口，加了之后 0 次，空闲期同样 0 次。

## 安全约束

- 写入前检测目标进程是否存活（存活则该端不写）
- 每次写入前备份目标存储（Qoder 备份整个 main.sqlite）
- 不删只加（本地删除不传播）
- 原子写入（tmp + rename / SQLite 事务）
- 干跑是默认：不带 `--apply` 只打印计划
- `pythonw` 下 `sys.stdout` 为 `None`，入口处兜底到 devnull，否则第一句 print 就抛

## 面板设计

- 纯 stdlib `http.server`，绑 `127.0.0.1:19528`，无框架依赖
- 服务端过滤自动化，前端只收人类对话
- 指标口径是**内容一致性**：差异 = 还能写但没写的尾部消息数；物理装不下的另列灰色数字，不算差异（否则永远红）
- 每 30s 自动刷新 + 「立即同步」按钮（按钮跑 `sync.py --apply`，`CREATE_NO_WINDOW`）
- 绿点 = 该端已有，灰点 = 缺失
