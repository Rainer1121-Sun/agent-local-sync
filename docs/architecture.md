# 架构设计详解

## 数据流

```
Agent A 关闭
    ↓
Watcher 检测进程退出（15s 轮询 tasklist）
    ↓
等待 3s（释放文件锁）
    ↓
sync.py --apply
    ↓
┌─────────────────────────────────────────┐
│ 1. 读取所有 agent 的会话（适配器）       │
│ 2. 过滤自动化（标题匹配）               │
│ 3. 归一化 ID（bare_id + 映射表）        │
│ 4. 取并集，计算各端缺失                 │
│ 5. 权威源优先选取版本                   │
│ 6. 备份目标存储                         │
│ 7. 写入增量（适配器 write_sessions）    │
│ 8. 验证读回                             │
└─────────────────────────────────────────┘
    ↓
Agent B 打开 → 看到 A 的对话
```

## 为什么不用服务端

agentctxsync 的完整方案是 FastAPI + PostgreSQL + TLS 反代，为跨设备设计。
单机场景下：
- 多一个进程 = 多一个挂的环节
- 多一个数据库 = 多一个备份/迁移负担
- 网络依赖 = 断网不可用
- 认证/密钥 = 不必要的复杂度

本方案：一个 Python 脚本 + 文件系统，零依赖外部服务。

## 为什么事件驱动而非定时

定时同步（每 N 分钟）的问题：
- agent 运行中写入会被覆盖（DSH 退出时覆写投影）
- 空跑浪费（没有新对话时也在读写）
- 延迟不确定（最坏等 N 分钟）

事件驱动（进程退出）：
- 天然满足"目标已关闭"的写入前置条件
- 只在有变化时触发
- 延迟 = 3s（等文件锁释放）

## 去重策略

三层：
1. **ID 归一化**：去掉 `session-` 前缀，统一为 bare UUID
2. **映射表**：Qoder 原生导入器会分配新 ID，用 migration_ledger 的 source_ref → target_session_id 映射回原始 ID
3. **权威源优先**：同一 ID 在多端都有时，取权威源（WB）的版本

## 安全约束

- 写入前检测目标进程是否存活（存活则拒绝）
- 每次写入前备份目标存储
- 不删只加（本地删除不传播）
- 原子写入（tmp + rename / SQLite 事务）
- Qoder 例外：WAL 模式允许运行中写入（busy_timeout=30s）

## 面板设计

- 纯 stdlib http.server，无框架依赖
- 服务端过滤自动化，前端只收人类对话
- 每 30s 自动刷新 + 手动"立即同步"按钮
- 绿点 = 该端已有，灰点 = 缺失
- 全绿 = 三方已齐
